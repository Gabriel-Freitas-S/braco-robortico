Checagem das versões publicadas: app (GitHub Releases) e firmware (main).

Roda em uma thread por checagem, entrega o resultado por mpsc e morre — o mesmo modelo de crate::link. A UI nunca espera rede: se não houver conexão, o resultado chega vazio e o app segue com o firmware embutido.

§Por que não a API do GitHub

A API sem token tem teto de 60 requisições por hora por IP e devolve 403 quando estoura (comum em laboratório atrás de NAT). Aqui a versão do app vem do redirect de github.com/.../releases/latest — HTML, sem cota — e o firmware vem de raw.githubusercontent.com, também sem cota.

§Segurança

  • Só HTTPS e só URLs fixas neste módulo; nenhuma resposta vira URL. A tag do app passa por firmware::valida_versao antes de montar o link da release com url_release, e o destino final de cada redirect é conferido contra o prefixo esperado.
  • Com timeouts e teto de leitura: host que não responde ou resposta gigante não travam a UI nem estouram a memória.
  • Nada é executado: o firmware é texto validado por firmware::validar e salvo como arquivo; uma versão nova do app só abre a página da release no navegador. Não há auto-update.
  • Falha vira linha no log, sem popup — a checagem é um extra, não um pré-requisito.

§Limites conhecidos

O firmware é lido de main. shortcut: main é a versão publicada neste projeto; se deixar de ser, troque a URL por tags fw-v*. Se o release mais recente do repositório for de firmware (tag fora de app-v), a versão do app fica desconhecida — de propósito, para não anunciar update falso.
